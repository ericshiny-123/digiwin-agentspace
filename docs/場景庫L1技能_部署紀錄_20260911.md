## 二、路由實測（1 題）

輸入：「幫我規劃一份 8 頁的簡報大綱，聽眾是製造業的資訊主管，目的是讓他們同意先做一家試跑」

結果：**正確路由到 L1-07**，且平台思考過程顯示三件事值得記錄：

1. **主 Agent 現在看得到 16 個技能**（15 張 L1 ＋ 既有的 vuln-dispatch），數量沒有造成路由失敗。
2. **描述裡的「不適用於…請用 L2-xx」邊界真的被拿來做路由判斷**——模型明確寫出
   「客戶提案大綱該用的 L2-SAL-02 不存在，但 L1-07 可用」，然後才選 L1-07。
   這證明邊界句是有效的設計，L2 之後上架時要沿用同樣寫法。
3. **卡片內的規則有被遵守**：模型在思考過程中覆述了「第一頁必須是結論、不要用大綱開場」與
   「需要數據的地方標 {待補數據：___}」。

### ⚠️ 同時發現一個會影響交付的行為

模型在真正啟用 L1-07 之前，**自己先去翻了記憶與郵件**（搜尋「製造業 試跑 簡報 提案 Pilot」、
查找並讀取兩封信），整段前置作業約占掉一半的回應時間與相應點數。

對交付的三個影響：

- **「五分鐘會用」的門檻可能被這段自主前置作業吃掉**，交付現場實測時要一併計時。
- **點數估算會被墊高**：放行清單必須項 #2《排程點數速查表》的實測，
  要把這種「模型自己加做的前置查詢」算進去，否則現場報給客戶的數字會偏低。
- **資料落地的說明要更明確**：模型會主動讀使用者的郵件。段 0 的《資料落地與管制說明》
  必須把「哪些情況下 AI 會主動存取信箱」講清楚，不能只講排程類卡片。

## 三、平台行為筆記（下次建技能直接沿用，不要重踩）

| # | 發現 | 影響與做法 |
|---|---|---|
| 1 | **平台會把 frontmatter 結束的 `---` 之後那個空行吃掉**，並確保檔尾恰好一個換行 | SKILL.md 要直接寫成這個「正規化後」的樣子（`---` 下一行就是 `# 標題`），否則讀回比對雜湊永遠差 1～2 個字元，會誤判成上傳損壞 |
| 2 | **技能顯示名稱會被 SKILL.md 的 frontmatter `name:` 覆寫** | 建立時 POST 的 name 會被檔案內容蓋掉；frontmatter 的 name 就寫成你要的完整顯示名稱。反向也成立：用 `PUT /api/skills/{id}` 改名時，平台會回頭改寫 SKILL.md 的 frontmatter name（內容其餘部分不動） |
| 3 | **POST 建立時帶的 `enabledTools` 沒有生效** | 建完要另外 `PUT /api/skills/{id}` 帶 `enabledTools` 一次；PUT 是部分更新（只送 name 不會清掉 description） |
| 4 | **base64 貼上損壞確實會發生** | 這次 15 張中有 1 張（L1-15）在貼上階段損壞，`atob` 直接丟錯。因為採「先解壓、先比對本機原檔 SHA-256、比對過才建技能」的順序，**損壞的那張沒有被建立，也沒有上傳半套內容**——這個順序要保留 |
| 5 | `GET /api/skills/{id}` 回傳的是 SPA 的 HTML，不是技能物件 | 要取單一技能請從 `GET /api/skills` 清單裡找；檔案則用 `/api/skills/{id}/file/SKILL.md` |
| 6 | 目前平台可用的 `enabledTools` 觀察到只有 `user_files`、`knowledge`、`ocr` | **沒有看到郵件、待辦、Wiki 對應的工具識別碼**。L1-01／06／12／15 這些排程卡實際能不能讀信箱與待辦，仍須向產品端確認（呼應方法論待確認 #1、#11） |
