# 場景庫 L1：檢討與優化建議

依據兩批實證：9/17 十五張逐張手動實測（含 v2 規則修正前後對照），
以及 9/18 四筆排程的**首次無人值守執行**。後者是第一次看到「沒有人在旁邊」時的真實行為，
價值高於任何一次手動測試。

## 一、v2 規則守住了什麼

| 項目 | 結果 |
|---|---|
| L1-12 不再修改既有待辦 | **守住**。無人值守下明確寫出「由於您指示不要修改或關閉任何待辦事項，故僅列出供您核對」，並主動指出一組資料矛盾（Heartbleed 主工單仍 pending，但複測紀錄顯示已 Closed）。這比原本「自己動手改掉」是更好的產品行為 |
| 不再誤遮蔽 | **守住**。L1-01 晨間摘要正常顯示客戶名與寄件人，產出可直接使用 |
| 不再主動亂翻 | **手動卡守住**（L1-02 由 19 動作降為 1）。**排程卡沒守住**，見 2.2 |
| 輸出格式 | L1-01 為 313 字、四區齊全、待辦標「未載明」，完全符合卡片設計 |

## 二、沒守住 / 新發現的問題（按優先序）

### 2.1 【最高】排程產出沒有送到任何地方 —— E 段的價值主張目前是空的

四筆排程跑完，摘要**只存在平台對話紀錄裡**。沒有寄信、沒有建待辦。

方法論 E 段的承諾是「產出送到信箱與待辦，明天早上不用他記得，也不用他特地登入」。
現況正好相反：**客戶必須登入平台、找到那則 Cron 對話，才看得到產出**。
這等於把「每天用」的唯一機制廢掉。

**這不是產品缺口。** 實測確認平台的 `mail` 工具支援 `send`／`reply`／`forward`／`send_draft`，
`task` 工具支援 `create`（個人待辦與企業待辦）。能力都在，是卡片沒有叫用。

根因：「產出必須送到信箱或個人待辦」這句寫在 SKILL.md 的**「排程設定注意」**區段裡，
那是寫給交付顧問看的設定提醒，**不是給模型執行的指令**；而「提示詞本體」裡沒有這一步。

**建議修法**：四張排程卡的提示詞本體最後加一步明確動作，例如
「完成後用郵件工具 send 把本摘要寄到我的信箱，主旨『晨間信件摘要 {日期}』」。
同時更新四筆 cron 的 prompt（cron 沒有技能綁定欄位，prompt 就是唯一入口）。

> 這一條沒修之前，四筆排程每天都在燒點數產出沒人看的東西。

### 2.2 L1-12 的「檢索升級」沒有被管住，只是被平台擋下

v2 管住了**寫入**，沒管住**找不到資料時的行為**。9/18 無人值守那次，L1-12 仍然：
`date` → `os.listdir('.')` → `os.listdir('..')` → `env` → 列出平台資料目錄
（列到 `db`、`skills`、`backup`、`.master-key` 等）→ 嘗試開 `cron.db` 讀 SQLite。
**單次執行 14 個 execute_command。**

擋下它的是平台回的 `Command rejected: no approval handler.`——
無人值守時沒有人能核准，所以自動拒絕。**這是運氣好，不是設計好。**
值得注意的是它把 `.master-key` 這個檔名帶進了對話紀錄。

**建議修法**：在 L1-12 的提示詞本體加停止條件——
「待辦工具回空或資料不完整時，直接輸出『目前查無待辦』並結束，
不得改用檔案、資料庫或指令等任何其他方式取得。」
規則要寫在**本體**，不是全域規則區（v2 已證明全域規則對這個行為無效）。

### 2.3 排程輸出長度失控

L1-01 的 313 字是對的。L1-12 同一次卻產出 8 個項目、每項五個欄位、大量 emoji 與分隔線，
長到沒有人會在早上九點看完。

**建議修法**：四張排程卡的提示詞本體加字數上限（L1-12 建議 300 字內、最多列 5 項，
其餘併成一行「另有 N 項可延後」）。這同時會降低點數。

### 2.4 ~~v2 把 L1-10 改壞了~~ —— 本條經複查後撤回

**原判斷有誤，已撤回。** 複查 L1-10 的卡片內容後確認：
「貼什麼進去」欄位本來就寫著「上次會議紀錄 + 本次議程」，
提示詞本體也已明寫「只根據我提供的紀錄，不要補充外部資訊」，
5 分鐘檢核第 3 條是「沒有出現我沒提供的外部資訊」。

這張卡從設計上就是貼入式的，v2 的「不主動檢索」與它完全相容。
9/17 實測時【我上次答應的事】顯示「查無」，是因為**測試時沒有貼上次會議紀錄**，
屬測試方法的疏漏，不是卡片缺陷。

因此原本建議的「允許讀取使用者指名來源」這個中間態**不予採納**。
考量 2.2 顯示放寬檢索的代價極高，現階段維持嚴格規則。

L1-10 真正待驗的問題是另一個：9/17 實測時它編造了合約條款
（99.99% 可用率、RTO/RPO、兩倍扣款）。v2 全域規則已加入
「原文沒寫的事實不得出現在產出裡」，**尚未重測驗證**，併入 2.6 處理。

### 2.5 排程實際執行時間不可靠

08:30 那筆在 **10:08** 才跑，09:00 那筆在 **10:03** 跑，晚了約 1.5 小時，
且補跑順序與設定順序相反。原因應是機器在時間到時未開機，平台採補跑機制。

**對交付的意義**：Edge 若裝在常開的主機上沒問題；裝在筆電上，
「明天早上不用你記得」這句承諾就不成立。
**段 A 的環境交付規格書要加一條硬體前提：排程主機需常時開機。**

### 2.6 三張卡尚未在 v2 下重測

L1-08（v2 才禁用 LaTeX 排版，未驗證）、L1-09、L1-10（原本是主動檢索與編造條款的案例）。
補測成本低，建議在建《排程點數速查表》時一併做掉。

## 三、建議新增的卡

### 3.1 【建議做】內部維運卡：排程健檢（不給客戶）

這次是靠人工翻 `/api/cron` 與對話紀錄，才發現「產出沒送出去」和「晚跑 1.5 小時」。
**交付 105 家之後，沒有這張卡，沒有人會知道客戶那邊的排程其實在空轉。**

內容：每週檢查各筆排程的 `lastStatus`、實際執行時間與排定時間的偏移、
被拒絕的危險指令次數、產出是否真的送達。屬 `mainAgentAccess` 內部工具，
比照 `vuln-dispatch`，不進 JD 品號目錄。

這張卡同時是放行清單必須項 #2《排程點數速查表》的資料來源。

### 3.2 【最高價值缺口，但卡在產品端】L2-MIS 六張

**L1 十五張全是通用 OA，沒有任何一張碰到製造業 IT 的真實痛點。**
方法論的核心主張是「窗口的動機來自 ERP 操作問答」，
但那張卡（L2-MIS-01）到現在一張都還沒建，仍卡在產品端待確認 #7。

現況等於：撐日活躍的 L1 已經可用，**撐窗口動機的那一層完全不存在**。
建議把 #7 的催辦優先度提到最高，這比再擴充 L1 有價值得多。

### 3.3 【不建議現在做】擴充更多 L1

41 張的規劃裡，L1 十五張是剛剛才穩定下來的（今天才第一次無人值守跑成功）。
在 2.1～2.4 修完、且 L1-06／L1-15 也跑過至少一輪之前，不要再加新卡。
**卡片數量不是瓶頸，卡片行為的可預測性才是。**

## 四、對方法論文件的修正建議

1. **段 A 環境交付規格書**：新增「排程主機需常時開機」硬體前提（依 2.5）
2. **段 E 排程設定**：設定步驟要包含「確認產出真的寄到信箱」的當場驗證（依 2.1）
3. **段 0 資料落地與管制說明**：補述 AI 在什麼情況下會嘗試存取檔案系統與資料庫，
   以及平台的核准機制如何攔截（依 2.2）——這是客戶一定會問的
4. **放行清單 #2**：點數速查表分「含／不含未知專有名詞」兩組，並納入排程健檢卡的實測數據
