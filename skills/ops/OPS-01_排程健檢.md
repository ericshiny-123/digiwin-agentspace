# OPS-01 排程健檢

> **內部維運技能，不在 JD 品號目錄內，不對客戶銷售。**
> 比照 `vuln-dispatch`，掛 `mainAgentAccess`，從首頁「新任務」直接叫用。

## 這張卡是什麼

| 欄位 | 內容 |
|---|---|
| 誰用 | 交付顧問、客戶成功團隊 |
| 什麼時候用 | 交付後第 7／14／30 天巡檢；客戶反映「怎麼沒收到」時 |
| 貼什麼進去 | 無需貼，直接讀平台排程資料 |
| 產出 | 一張健檢表 ＋ 異常清單（每項含判定依據與建議處置） |
| 要改的參數 | ①偏移容忍值（預設 30 分鐘） |
| 可否排程 | 是（建議每週一次） |
| 對客戶的好處 | 不用等到客戶抱怨才發現排程在空轉；交付後的用量承諾有實際數據可佐證 |

## 任務辨識

使用者出現下列意圖時啟用本技能：「排程健檢」「排程有沒有在跑」「檢查定期任務」
「客戶說沒收到晨間摘要」「定期任務巡檢」

不屬於本技能的情況：要建立、修改、停用或手動執行某個排程 —— 本技能唯讀，請改用平台
「定期任務」頁面自行操作，不要勉強套用本卡格式。

## 提示詞本體（直接套用，{} 內為要改的參數）

```
用 cron 工具的 list 與 history 動作，檢查目前所有定期任務，輸出健檢表。

偏移容忍值：{30} 分鐘

【健檢表】每筆排程一列：
名稱｜cron 運算式｜上次執行｜狀態｜下次執行｜偏移｜產出是否送達

【異常清單】只列有問題的，每項寫：哪一筆、依據、建議處置

判定規則（逐條比對，不得心算日期）：
1. 下次執行距今超過 8 天 → 標「排程時間異常」。
   已知平台缺陷：指定單一星期幾（如 `0 16 * * 5`）時，
   下次執行會被算到某個「某月 1 日剛好是該星期幾」的日期，可能數年後。
   處置：改成每日觸發（`* * *`）＋ 在提示詞最前面加星期守門條件。
2. 上次執行時間與該次排定時間相差超過容忍值 → 標「執行延遲」。
   常見原因是排程主機在排定時間未開機，平台採補跑。
   處置：確認主機是否常時開機；若為筆電，需調整交付時的硬體前提說明。
3. lastStatus 不是 success → 標「執行失敗」，附狀態值與重試次數。
4. 該筆排程的產出若設計上要寄信或建待辦，檢查最近一次執行的結果裡
   有沒有「已寄出」之類的完成回報 → 沒有就標「產出未送達」。
   這一項最容易被忽略：排程跑成功不等於使用者收得到。

規則：
- 只用 cron 工具的 list 與 history 兩個動作，以及對話紀錄。
  **不得呼叫 create、update、delete、toggle、run**，也不得用檔案、
  資料庫或系統指令去取得排程資料。
- 取不到資料就寫「查無」，不得推測。
- 全文控制在 500 字內；一切正常時就寫「N 筆排程全部正常」，不要湊字數。
```

## 全域規則（每次執行都適用）

- **只讀取本卡明確授權的來源**（cron 工具的 list 與 history、平台對話紀錄）：
  不另外搜尋郵件中心、我的記憶、檔案總管或知識庫，也不執行任何查詢平台資料庫或
  檔案系統的指令。授權來源取不到資料時直接說「查無」，**不要改用其他方式去找**。
- **本技能為唯讀**：不建立、不修改、不停用、不手動執行任何排程；
  不新增或修改待辦、不寫入檔案、不變更平台紀錄、不寄送任何郵件。
- **產出一律視為草稿**，對外發送或正式使用前必須由人覆核。
- **原文沒寫的事實不得出現在產出裡**：時間、狀態、次數沒有依據就寫「查無」或標 {待補}。
- 算式用純文字寫（例如 偏移 = 10:08 − 08:30 = 98 分鐘），不要使用 LaTeX 或數學排版。
- 全程繁體中文（台灣用語）。

## 5 分鐘檢核（交付現場用）

1. 健檢表列出的排程筆數與平台「定期任務」頁面一致
2. 故意把一筆排程設成 `0 16 * * 5`，健檢能抓出「排程時間異常」
3. 對一筆設計要寄信的排程，能正確判斷產出有沒有送達
